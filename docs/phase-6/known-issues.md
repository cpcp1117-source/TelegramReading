# Phase 6 Known Issues

Phase 6 Gate has not been evaluated yet (Slice 1 -- Risk Engine -- is in
progress; see [phase-kickoff.md](phase-kickoff.md)). This file tracks real
engineering judgment calls made building Slice 1, none of which were
resolved by an existing spec value -- system-spec.md leaves TBD-003 and
several contract questions explicitly open, and account/market data
sourcing has no precedent before this phase.

## Slice 1 Scope and Limitations (by design, not oversight)

| ID | Item | Detail |
|---|---|---|
| P6-LIMIT-001 | `AccountState` (equity, open positions, daily realized loss) is a Slice-1 configuration/self-tracking approximation, not real Binance account data | No Execution Gateway exists yet to query a real account (Slice 2's job). `default_starting_account_state` always starts a run from a clean slate (zero open positions, zero margin used, zero daily loss); within one run, approved intents accumulate against each other (so a batch of several signals in one run doesn't each pretend the account is empty), but that state is discarded between runs. `equity_usdt` comes from the required `RISK_EQUITY_BASELINE_USDT` config value, not a real balance query. BR-010's "existing manual positions also count" cannot actually be satisfied until Slice 2. |
| P6-LIMIT-002 | TBD-003 (system-spec.md, explicitly "Blocking Gate 6"): the ROE-to-stop-price formula is the baseline leverage-only calculation, no fees/funding/maintenance margin/slippage buffer | `risk_engine.compute_roe_stop_price`: `entry * (1 - roe_pct/leverage)` for LONG, `entry * (1 + roe_pct/leverage)` for SHORT. Documented in the function's own docstring as incomplete, not silently assumed precise. Needs the CS-BN-004 Testnet contract spike (Slice 2) to refine. |
| P6-LIMIT-003/004 | **Resolved 2026-09-16** -- BR-006's raw elapsed-time freshness check (60s source age) rejected almost every real signal under the manual-approval workflow | Confirmed live: the very first two real signals evaluated (`LSK`, `HIVEUSDT`) were both rejected, `HIVEUSDT`'s rejection including `SOURCE_TOO_OLD` despite being approved the same day it was posted -- exactly the predicted failure mode. Discussed with the user 2026-09-16; decided to replace the raw-elapsed-time check with BR-006's own (previously unimplemented) price-deviation leg for `MARKET` entries instead: `binance_market_data.fetch_reference_price` (public `/fapi/v1/klines`, no credential) fetches the price near the signal's original post time, `risk_engine.evaluate_trade_intent` compares it to the current mark price and rejects only if the market actually moved more than `max_price_deviation_bps` (50bps default) -- regardless of how much time passed. A five-minute-late approval on an unmoved price is now fine; a ten-second-old approval after a sharp move is not. `max_source_age_seconds` removed entirely (migration `0015`, dropped from `risk_config_snapshot`); `max_receive_lag_seconds` (collector-health, unrelated to approval delay) unchanged. New reason codes `PRICE_DEVIATION_TOO_HIGH`/`REFERENCE_PRICE_UNAVAILABLE` replace `SOURCE_TOO_OLD`. |
| P6-LIMIT-005 | **Superseded 2026-09-25, same day as its own resolution -- see P6-NOTICE-007** -- Sizing (BR-009) originally took the **minimum** of three independently-computed quantities (risk-based, single-trade margin cap, remaining total-margin headroom) | Confirmed as-is earlier the same day, then superseded hours later once the user described their actual practice: stop-loss is set by chart structure (prior swing low/high), not derived from a risk-based stop distance, making a stop-distance-keyed sizing cap meaningless. Left here for the decision trail, not because the behavior still exists -- see P6-NOTICE-007 for what replaced it. |
| P6-LIMIT-006 | `trade_intent.status` is written once, fully resolved (`RISK_APPROVED`/`RISK_REJECTED`), never literally `CREATED` | The logical state machine (logical-data-model.md §4) describes `CREATED -> RISK_APPROVED/RISK_REJECTED` as if there's a gap between creation and evaluation. In this slice's implementation, evaluation and creation happen atomically in the same transaction (the row is append-only, so there is no later UPDATE to transition it) -- `CREATED` is accepted by the schema's CHECK constraint for a future slice that might need a real two-phase flow, but Slice 1 never writes it. |
| P6-LIMIT-007 | `risk_decision.expires_at` is recorded (`RISK_DECISION_EXPIRY_SECONDS`, default 300s) but not yet enforced by anything | Same "recorded now, enforced by a future consumer" pattern as `normalized_signals.expires_at` was in Phase 4 before the Control Bot's `expires_at` fix gave it a reader. Slice 2 (Execution Gateway) is the natural place to check it before submitting an order. |

## Slice 2a Implementation -- Real Bugs Found via Live Testnet Verification (2026-09-28)

Per the user's instruction to self-test and fix rather than pause for each issue, `scripts/execute_trade_intents.py` was run repeatedly against real Testnet orders (not mocks) until a clean, unattended run completed end-to-end. Four real defects were found and fixed this way -- none were caught by unit tests, since all four are shapes of "what the live API actually returns/enforces" that a hand-written fake would have had to independently guess correctly to catch.

| ID | Item | Detail |
|---|---|---|
| P6-NOTICE-010 | `POST /fapi/v1/algoOrder` is required for `STOP_MARKET`/`TAKE_PROFIT_MARKET` -- see [api-contract-inventory.md](../phase-0/api-contract-inventory.md)'s corrected CS-BN-002. This overturns this file's own P6-NOTICE-006/CS-BN-002 note from 2026-09-25. | `binance_trading_client.py` gained `place_algo_order`/`get_algo_order`; `execution_gateway._place_and_confirm_protection` uses them (`algoStatus`/`algoId`, not `status`/`orderId`). A placed algo order does not appear in `GET /fapi/v1/openOrders` -- only `GET /fapi/v1/algoOrder` (by `algoId`/`clientAlgoId`) can confirm it, confirmed live. |
| P6-NOTICE-011 | Three schema/constraint bugs, each found by a real `CheckViolation`/`UniqueViolation` mid-run, none guessable from the spec alone | (1) `position_snapshot.margin_type` allowed `'CROSSED'`; Binance actually returns `"cross"`/`"isolated"` (this module upper-cases to `CROSS`/`ISOLATED`) -- fixed to `'CROSS'`. (2) `exchange_order.status` was populated with this project's own `OrderLifecycle` FSM words (`PENDING_SUBMIT`/`SUBMITTED`) instead of Binance's real order-status vocabulary (`NEW`/`PARTIALLY_FILLED`/.../`TRIGGERED`) -- the two are different vocabularies for different things and were conflated when the table was designed; fixed the CHECK constraint to Binance's real values plus this module's own `UNKNOWN` sentinel. (3) `order_lifecycle.entry_client_order_id` had its own `UniqueConstraint`, which is wrong: the same `entry_client_order_id` is *supposed* to repeat across every revision of one lifecycle (that's the whole idempotency point) -- the constraint was rejecting a lifecycle's own second revision. Dropped; `UniqueConstraint(intent_id, revision)` alone is correct and sufficient. All three fixed directly in migration `0017` (not a new migration `0018`) since the tables had zero real rows at the time -- this is noted here rather than silently amended because it's exactly the kind of change this project's own convention (see migration `0015`'s docstring) would otherwise flag. |
| P6-NOTICE-012 | `trade_intent` has a hard `BEFORE UPDATE` trigger (`reject_trade_intent_update`, migration `0014`) making it genuinely append-only -- confirmed by a real crash, not by re-reading the migration first | The original design assumed `RISK_APPROVED -> SUBMITTED/EXPIRED` would be written by updating `trade_intent.status` in place. That is not possible; the trigger unconditionally rejects it. Fixed: `execution_gateway.py` no longer touches `trade_intent` after its creation at all -- `_record_execution_outcome` only appends an `audit_events` row. "Has this intent been executed" is entirely derived from whether an `OrderLifecycle` row exists for it (`load_eligible_intents`'s own query), the same "derive current state from the latest related row, never mutate the origin row" convention this codebase already uses for `NormalizedSignal`/`RiskConfigSnapshot`/etc. `trade_intent.status` therefore reads `RISK_APPROVED` forever, even after real execution -- this is now expected, not a bug, but worth knowing if anyone queries that column directly expecting it to reflect execution state. |
| P6-NOTICE-013 | Confirmed live (see CS-BN-002's note above): `newClientOrderId` idempotency only holds while an order is *active* | During this same testing, a retried run reused an entry order's `clientOrderId` after the original had already filled (closed), and Binance accepted it as a genuinely new order rather than deduplicating -- resulting in a real double-fill (6696.8 XRP instead of 3348.4 across two runs). Caught and manually closed out on Testnet (no lasting position left open). **Fixed 2026-09-29, see P6-NOTICE-018.** |
| P6-LIMIT-012 | The `fill` table is never actually populated -- `_record_fills` is called with the entry/protection *order* response object, which has no per-trade `id`/`qty`/`commission` fields (those live on `/fapi/v1/userTrades`, a different endpoint never called) | `exchange_order.filled_quantity`/`avg_fill_price` (populated correctly from the order object) are what sizing/protection actually use, so this does not affect Slice 2a's safety behavior -- it only means the granular per-trade audit table FR-020/reconciliation would eventually want is silently empty. Needs a `get_user_trades` client method and a real call site before Gate 6/7, not required for Slice 2a's own correctness. |

All of the above were found and fixed against a real Testnet account, not a simulation: a genuine XRPUSDT position was opened, (mis)protected, and closed multiple times during this process, ending flat with no open position or resting order. The final clean run (after all four fixes) completed unattended end-to-end: entry submitted -> fill confirmed -> `STOP_MARKET` algo protection order placed and confirmed, all in one process invocation with no manual intervention.

| P6-NOTICE-021 | **A failed protection or take-profit placement is retried once, within 5 seconds, and every attempt's outcome is notified** (explicit user request, 2026-09-29) | `_place_with_one_retry` wraps both `_place_and_confirm_protection` and `_place_and_confirm_take_profit` (which now return a `PlacementAttempt` carrying the failure reason instead of a bare `None`). On a first failure it first looks up the original `clientAlgoId` -- a placement that raised may still have landed, and adopting it avoids stacking a second reduce-only order -- then sends `execution_protection_retrying`/`execution_take_profit_retrying` (attempt 1 + reason), waits 1s, and retries once under a distinct deterministic id (`retry_client_order_id_for`). The retry is skipped, and reported as such, if it cannot start within 5s of the failure. The final `*_confirmed`/`*_failed` notification carries `attempt` (1 or 2) and, on failure, both attempts' reasons. The protection retry gets its own FR-019 confirmation deadline. **Entry orders are deliberately not retried** (confirmed by the user) -- see P6-NOTICE-022. Covered by five `_place_with_one_retry` unit tests and integration test `test_execute_one_retries_failed_protection_and_notifies_each_attempt`. Not yet exercised against live Testnet (would need a placement that genuinely fails once). |
| P6-NOTICE-022 | **A failed entry order is notified, never resubmitted** (explicit user request, 2026-09-29) | `_execute_one` catches an entry placement failure and sends a dedicated `execution_entry_failed` notification (symbol, side, type, quantity, price, `client_order_id`, reason) instead of falling through to the generic `execution_unexpected_error`; result `ENTRY_FAILED`. The revision-0 `order_lifecycle` row stays at `PENDING_SUBMIT`, so no later run picks the intent up again. Found while testing this: when the POST failed and the follow-up lookup returned `-2013`, `_place_order_idempotent` raised the *lookup's* "Order does not exist." and hid the real cause (e.g. `-2019 Margin is insufficient.`).
